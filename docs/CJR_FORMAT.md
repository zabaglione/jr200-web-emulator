# CJRコーデック仕様 v0.1
根拠: `UPSTREAM.md` S3。対象は公開コードから確認できる標準ブロック構造であり、メーカー公式仕様の網羅を主張しない。

## 1. 構造
バイト順はアドレスのみbig-endian。データは任意の8-bit値。CJRはWAVではなく、リーダー・音量・実際の波形を含まないバイト列である。

### ヘッダーブロック（33バイト）
| オフセット | 長さ | 内容 |
|---|---:|---|
| 0 | 2 | 02 2A |
| 2 | 1 | ブロック番号00 |
| 3 | 1 | ペイロード長1A（26） |
| 4 | 2 | 通常FFFF |
| 6 | 16 | JRファイル名の生バイト。Unicodeではない |
| 22 | 1 | 00=BASIC、01=マシン語。未知値は警告付き保持 |
| 23 | 1 | 生のbaud指定。上流は00を2400、非0を600として扱う。CLI/Webの新規作成はJR2Rescue実出力に合わせ、600を0x64（10進100）で記録 |
| 24 | 8 | 生成時はFF。読込時は元の値を保持 |
| 32 | 1 | 0〜31の加算値mod 256 |

### データブロック（N+7バイト）
02 2A / ブロック番号 / 長さ / 開始アドレス上位・下位 / データNバイト / checksum。
長さ00は256バイト。checksumはそのブロックの02から最終データまでの加算値mod 256。標準writerはブロック番号01〜FE、最大254ブロックを生成する。

### フッター（6バイト）
02 2A FF FF / アドレス上位・下位。チェックサムは付かない。標準writerはデータ末尾の次のアドレスを出す。読み取り時は元のフッターを保持し、最終領域末尾と異なる場合は警告だけを出す。このアドレスを実行開始PCと決めつけない。

## 2. 対応範囲
通常BASIC/マシン語CJRの検査、BIN→単一領域CJR、検証後の損失なしコピー、明示指定によるヘッダーなし形式の検査に対応する。BASIC生成指定では格納先を$0801にするが、入力BINをBASICプログラムに変換・トークナイズする機能ではない。

1つのヘッダーの後に離れたアドレスのデータブロックが並ぶマルチ領域を保持する。CLI extractはアドレスが非連続なら拒否する。複数の完全なCJRファイルを単純に連結した入力は末尾データとして拒否する。マルチ領域と複数ファイル連結を混同しない。

## 3. 安全性と保存則
- 最大入力1 MiB。入力は読み取り専用。加算前の残長チェックで領域外アクセスを防ぐ。
- summaryは検証成功時だけ更新。visitorはファイル全体を検証してから呼ばれる。
- checksum不一致を勝手に修復しない。未知種別・非標準ヘッダー値・番号の飛び・非連続アドレス・フッター差分は警告として返す。
- データブロック内で16-bitアドレス領域を越えたら拒否。末尾が65536になることは許容し、summaryでは32-bit値として保持する。
- 構造化読込後の再構築で未知のバイトを失う方式ではなく、検証済みの原バイトをコピーするlossless経路を用意する。
- 書込失敗時は出力を部分更新しない。入力と出力の重複はAPI契約上禁止（copy_verifiedの同一ポインタを除く）。
- 名前は16生バイト。ブラウザの新規作成UIではASCII 1〜16文字に限定する。JR文字コード変換は別Issue。

## 4. C ABI v1
`src/wasm/api.cpp`の関数は、Webとnativeテストで同じ実装を呼ぶ。
入力/出力バッファはそれぞれ1 MiBで、ポインタと容量を公開する。`jr200_inspect(size, allow_headerless)`の戻り値0は構造検証成功。非0は`Error`値で、エラー位置と静的メッセージを別関数から読む。summaryは構造体のメモリ配置を直接公開せず、`jr200_summary_field(index)`で取得する。

`jr200_encode`では入力先頭16バイトを名前、続く領域をペイロードにする。呼び出し間で出力・summaryは更新されるため、必要なデータはJS側にコピーする。単一インスタンスは再入不可。将来CPU側で複数マシンが必要になった時にハンドルAPIへ拡張する。

## 5. いまのテスト証拠と限界
47バイトの手計算golden、境界長、全256バイト値、破損・切断、名前・アドレス・バッファ検証、1万2,000件の変異/不正入力を用いる。nativeとWASMで同じgoldenを確認する。加えてJR2Rescue 0.6.2のWindows向けバイナリをMono上で実行し、標準MSAVE/BASICの全バイト一致、相互読込、600/2400、マルチ領域、headerlessを自作データで対照した。詳細は [P03_REFERENCE_RESULTS.md](P03_REFERENCE_RESULTS.md)。これはネイティブWindows、VJR-200、実機録音、JR-200実機互換の証拠ではない。

## 6. 波形層に持ち越す確認事項
S3のBitGetterDはstart=0、LSB-firstの8データビット、stop=1が3個という12ビットを作る。GetLoadDataは先頭ブロックを600baudで扱い、後続でbaud指定を反映する。WaveGetterでは600baudの0/1で波形パターンが異なり、2400baud側には位相符号の継続処理がある。一般的なFSK/KCSの印象だけで極性・周波数割当・停止ビットを決めない。

リーダー/インターミッションの定数だけから全WAVを決めず、GetLoadDataの制御フローと既存ツールの実出力を対照する。JR2Rescueがヘッダーなし入力を`CJRtoJR2`で受理することは確認したが、同形式の直接WAV化や実機読込は未確認である。44.1kHzは1ビットを整数サンプルに丸め続けるとドリフトするため、累積位相/有理数時刻で処理する。WAV合成はP10、標準CJRへのWAV復元はP11で追加したが、実機往復はP12まで未検証である。
